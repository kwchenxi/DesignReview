# Design Review - 设计还原度审查

对比设计稿与实现页面的视觉差异，结合客观量化指标与 AI 语义分析，输出还原度评分和结构化问题清单。

---

## 何时使用

当设计师、产品经理或工程师需要验证线上实现是否还原了设计稿意图时使用。典型场景：

- 发布前设计验收
- 上线后回归检查
- 设计与开发交接确认
- 视觉还原度专项排查

---

## 执行前确认

- 确认用户提供了两个输入：页面侧（截图或URL）+ 设计稿侧（截图或Figma链接）
- 确认审查范围：整页 / 指定区域 / 单个组件
- 如需 AI 分析，确认 .env 中已配置 AI_API_KEY

---

## 根据输入构建命令

### 场景 A：两张截图对比（算法模式，最常用）
```bash
npx ts-node src/cli.ts check -p <页面截图路径> -g <设计稿截图路径>
```

### 场景 B：截图 + AI 分析（双引擎模式）
```bash
npx ts-node src/cli.ts check -p <页面截图路径> -g <设计稿截图路径> --ai
```

### 场景 C：URL 页面 + 设计稿截图
```bash
npx ts-node src/cli.ts check -u <页面URL> -g <设计稿截图路径>
```

### 场景 D：URL + Figma 链接（需要 FIGMA_ACCESS_TOKEN）
```bash
npx ts-node src/cli.ts check -u <页面URL> -f <Figma链接>
```

### 场景 E：启动 Web UI
```bash
npm run web
```
然后告知用户浏览器访问 http://localhost:3456

## 审查维度

无论算法模式还是 AI 模式，均应覆盖以下维度（用户可指定聚焦范围）：

### 1. 布局与结构
- 缺失或多余元素
- 模块顺序差异
- 对齐问题
- 间距不一致
- 栅格错位
- 文字意外换行或截断

### 2. 视觉样式
- 字体层级不匹配
- 字号、字重、行高偏差
- 颜色、透明度、阴影偏差（由 CIE76 DeltaE 量化）
- 圆角、边框偏差
- 图标风格不一致
- 图片裁切或比例问题

### 3. 文案与内容
- 措辞不一致
- 占位文案未替换
- 文字截断或溢出
- 大小写或术语不一致
- 缺少辅助说明或标签

### 4. 组件状态
- 默认态、悬停态、聚焦态、禁用态、加载态
- 空状态、错误状态、成功状态
- 选中/未选中行为
- 骨架屏/加载占位

### 5. 交互预期
- 缺少交互反馈
- 点击/触摸区域不正确
- 弹窗、提示、Toast 行为差异
- 导航结果不一致
- 缺少关键动画

### 6. 无障碍与可用性
- 对比度不足
- 字号不可读
- 触摸目标过小
- 控件被遮挡
- 焦点行为不明确

## 严重度框架

统一使用四级分类：

| 级别 | 英文 | 含义 |
|------|------|------|
| **严重** | Critical | 阻断发布、核心流程不可用、重大设计/可用性失败 |
| **主要** | High | 关键区域显著偏差，应在验收前修复 |
| **次要** | Medium | 影响精致度、层级感或一致性的可感知偏差 |
| **建议** | Low | 细节质量问题，不阻断的非视觉优化建议 |

同时按类型标签分类：布局 / 视觉 / 文案 / 状态 / 交互 / 无障碍

## 执行流程

### Step 1 — 归一对比基线
确认或推断：
- 对比的是同一页面/同一状态
- 同一设备尺寸或视口
- 同一主题模式、语言环境
- 尽量同一数据条件

如基线不可比，先指出再审查。

### Step 2 — 算法引擎执行
CLI 命令执行后，代码引擎自动完成：
- 像素级差异检测（pixelmatch）
- CIE76 DeltaE 感知色差计算
- 容差按属性独立判定
- 生成客观评分与数值报告

### Step 3 — 全局扫描
从高层差异入手：
- 页面层级
- 主要模块
- 明显缺失或多余的 UI
- 主 CTA 突出度
- 整体平衡与视觉节奏

### Step 4 — 细节审查
按审查维度逐项检查：布局 → 视觉样式 → 文案 → 状态 → 交互 → 无障碍

### Step 5 — 归类与排序
- 合并重复问题
- 按区域或组件分组
- 优先展示 Top 3 风险
- 区分阻断问题与优化建议

### Step 6 — 产出报告

---

## 执行后汇报

1. 总体评分（X / 100）
2. 问题统计（严重 X / 主要 X / 次要 X / 建议 X）
3. Top 3 风险项
4. 关键问题清单
5. 推荐修复顺序
6. 报告文件路径

## Issue 卡片模板

每个问题按以下结构输出：

### Issue {序号} — {简短标题}
- **严重度：** {严重 / 主要 / 次要 / 建议}
- **区域：** {页面/模块/组件}
- **类型：** {布局 / 视觉 / 文案 / 状态 / 交互 / 无障碍}

**现状**
描述当前实现的精确表现。

**预期**
描述设计稿的意图或预期行为。

**影响**
说明为何重要（层级感、可用性、一致性、转化率等）。

**建议**
以实现角度描述最可能的修复方式。

**依据**
- 设计稿参考：{frame 名称 / 链接 / 截图标注}
- 实现参考：{URL / 截图标注 / DeltaE 数值 / 像素差百分比}

## 写作规则

- 像资深设计师与工程师沟通的语气
- 不用模糊表述（"感觉不对"、"差点意思"）
- 方向、间距、层级、对齐、状态、行为必须具体
- 先呈现重要问题，不要被细节淹没
- 使用中性措辞，如"当前实现与设计意图存在偏差"
- 优先强观察，少做推测性判断
- 算法模式产出的 DeltaE 数值、像素差百分比等客观数据必须保留

## 技术特性（供参考）

- 像素对比引擎：pixelmatch，支持抗锯齿容差
- 色差计算：CIE76 DeltaE 感知色差算法，容差可按属性独立配置
- AI 分析支持：OpenAI / Anthropic Claude / DeepSeek / 兼容接口
- 输出格式：HTML（可视化）+ Markdown
